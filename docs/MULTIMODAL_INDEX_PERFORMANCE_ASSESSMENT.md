# PastVideo 多模态索引性能评估

> 日期：2026-08-02
>
> 状态：现有视觉索引为本机实测；Caption、OCR、Whisper 和融合索引为实施前工程估算，必须在阶段 A 用真实 Worker 重新校准。

## 1. 结论

当前本地 Qwen 视觉索引在这台 RTX 4090 D 主机上有两种可观察水平：

- 固定基准视频：约 **78.5× 实时速度**，即索引 1 小时视频约需 0.76 分钟。
- 真实长视频集合：约 **28.1× 实时速度**，即索引 1 小时视频约需 2.13 分钟。

产品规划应采用更保守、更接近真实磁盘、编码格式和长文件切换开销的 **28×** 数据作为当前基线。

加入本地 Caption、OCR、Whisper 和文本索引后，在复用解码结果、限制 OCR 帧数并采用保守串行 GPU 调度的前提下，完整理解预计达到：

- **平衡配置：5–10× 实时速度**。
- 每小时视频约需 **6–11 分钟**。
- 相对当前真实视觉索引，完整处理时间增加约 **3–5 倍**。
- 吞吐下降约 **65%–80%**。

这不应等同于“用户要多等 3–5 倍才能搜索”。如果视觉索引优先发布，现有视觉可搜索时间预计只增加 **0%–10%**；Caption、OCR 和转录随后增量加入结果。

真实结果比固定 benchmark 慢约 2.8 倍。可能原因包括：

- 多个长文件之间的打开、探测和解码器切换。
- 源编码、分辨率、磁盘访问和关键帧分布不同。
- 批次边界不总能填满。
- 真实运行包含模型启动、数据库提交和更多编排开销。

因此后续容量规划以 2.13 分钟/视频小时为视觉基准。

## 3. 新能力的工作量模型

真实数据平均每小时视频产生约 145 个重叠片段。估算采用以下平衡配置：

- Caption：每个片段使用 6–8 张复用代表帧，生成不超过约 96 个 token 的结构化 JSON。
- OCR：每片段只识别 2–4 张经过画面变化过滤的代表帧。
- Whisper：使用 `faster-whisper`、VAD 和本地 GPU；音频流式处理。
- 文本向量：Caption、OCR 和 Transcript 先按时间片段聚合，再批量生成 embedding。
- GPU：第一版大模型串行，CPU/NVDEC 预处理有限流水并行。
- FTS5 和数据库写入增量执行。

按每小时源视频估算：

| 阶段 | 当前/预计耗时 | 主要瓶颈 | 置信度 |
| --- | ---: | --- | --- |
| 现有视觉 embedding | 2.13 分钟 | 解码 + Qwen 推理 | 已实测 |
| Caption | 3–6 分钟 | 视觉编码 + 文本生成 | 中低 |
| OCR | 0.4–1.2 分钟 | 帧解码 + 检测识别 | 中 |
| Whisper | 0.6–1.5 分钟 | 音频解码 + ASR 推理 | 中 |
| 文本 embedding + FTS5 | 0.2–0.6 分钟 | Qwen 文本推理 + SQLite | 中 |
| **完整合计** | **6.3–11.4 分钟** | Caption 为主 | 工程估算 |

中位估算约为每小时视频 8.5 分钟，即：

- 约 **7.1× 实时速度**。
- 相对当前 2.13 分钟增加约 **4 倍墙钟时间**。
- 吞吐由每墙钟小时处理约 28 小时视频，降为约 7 小时视频。

## 4. 不同质量配置

| 配置 | 策略 | 每小时视频预计耗时 | 实时倍速 | 相对当前耗时 |
| --- | --- | ---: | ---: | ---: |
| 快速 | Caption 稀疏采样、OCR 低帧数、Whisper Turbo | 4–6 分钟 | 10–15× | 1.9–2.8× |
| 平衡 | 每个 30 秒窗口 Caption、OCR 变化帧、Whisper Turbo | 6–11 分钟 | 5–10× | 3–5× |
| 高质量 | 更密集 Caption/OCR、较大 Whisper、更多生成 token | 12–20 分钟 | 3–5× | 5.6–9.4× |

建议桌面默认采用平衡配置，并允许用户只启用 OCR、语音或描述。Caption 是最大的新增成本，预计占新增时间的 55%–75%。

## 6. 用户感知性能

推荐把状态拆成两层：

1. **视觉已索引**：现有自然语言/图片搜索立即可用。
2. **理解已增强**：Caption、OCR、转录逐项加入搜索。

每个视频的调度顺序建议为：

```text
视觉 embedding → 立即发布 → Whisper/OCR/Caption → 文本索引 → 融合就绪
```

这样可以达到：

- 扫描文件夹速度不变。
- 第一个视频进入搜索的时间基本不变。
- 已视觉索引的视频不等待 Caption。
- 每完成一种模态，搜索结果立即获得新的证据。
- 停止任务时，已完成视觉索引和 Artifact 都保留。

如果强制等待四种模态全部完成后才把视频标记为可搜索，用户感知等待会直接增加 3–5 倍，不推荐这种设计。

## 7. 存储和搜索开销

### 7.1 索引存储

当前视觉数据库约为每视频小时 1.23 MB。新增三个 2048 维文本向量投影和原始文本后，预计：

- 平衡配置约 **5–10 MB/视频小时**。
- 相对当前约增加 **4–8 倍**。
- 4.34 小时集合预计约 22–45 MB。
- 100 小时媒体库预计约 0.5–1.0 GB。

模型文件和临时帧不计入索引数据库。临时帧和音频必须有界并在安全提交后清理。

### 7.2 搜索延迟

融合查询会并行或顺序扫描视觉、Caption、OCR、Transcript 和 FTS5 候选：

- 向量比较总量约增加到当前的 3–4 倍。
- 当前数千片段规模下，预计仍能保持交互式响应。
- 文本 query embedding 通常比 FTS5 和排名融合更昂贵，因此端到端延迟不一定线性增加 4 倍。
- 到数万或十万片段后，当前暴力余弦扫描会成为明显瓶颈，需要 HNSW 或其他 ANN 索引。

由于目前没有融合实现，这里不提供虚假的毫秒数字。阶段 C 必须测量持久 Worker 下的 P50/P95，并分别报告冷启动和热查询。

## 8. GPU、CPU 和内存影响

当前视觉 benchmark 峰值显存约 10.3 GB。预计单模型运行时：

- Qwen Caption 4B：约 10–18 GB，受帧数、分辨率和生成长度影响最大。
- Whisper：约 2–6 GB，取决于模型和计算精度。
- OCR：通常低于 Caption，但实现前需要实测。

如果大模型同时常驻，24 GB 显存可能不足或使 batch 显著下降。因此第一版串行 GPU 许可更稳妥。Caption 优化稳定后，再验证 Qwen Embedding 与 Whisper 是否可以安全共存。

CPU 侧最大的风险仍是重复解码。若 Caption、OCR、视觉各自重新读取视频，完整耗时可能额外增加 20%–50%，并再次出现 CPU 成为瓶颈。必须使用统一帧抽取/缓存层，Caption 与 OCR 复用视觉代表帧。

## 9. 推荐性能预算

将以下数字作为实现阶段的验收目标：

| 指标 | 目标 | 需要调查/阻止发布 |
| --- | ---: | ---: |
| 视觉可搜索路径回归 | ≤10% | >15% |
| 平衡配置完整处理 | ≤10 分钟/视频小时 | >15 分钟/视频小时 |
| 真实 4.34 小时集合 | ≤45 分钟 | >65 分钟 |
| GPU 峰值显存 | <22 GB | 接近 OOM 或频繁降 batch |
| CPU 内存 | 稳态 <75% | 单调增长或达到 90% |
| 重启/恢复 | 无重复记录 | 丢失进度或重复候选 |
| 热搜索 P95 | 阶段 C 校准后冻结 | 不能保持交互式响应 |

## 10. 最有效的优化顺序

1. **视觉优先发布**：保护当前约 28× 的可搜索体验。
2. **一次解码，多处复用**：视觉、Caption 和 OCR 共用代表帧。
3. **控制 Caption 成本**：短 JSON、限制输出 token、批处理、避免重叠窗口重复描述。
4. **OCR 变化帧过滤**：不对连续相似字幕重复识别。
5. **Whisper 流式 + VAD**：避免全音频常驻内存。
6. **文本 embedding 批处理**：在 Artifact 完成后集中处理。
7. **真实查询评测后调权**：不要用更多计算换取没有验证的融合复杂度。
8. **大规模前引入 ANN**：避免四路暴力向量扫描限制搜索扩展。

## 11. 评估边界

以下数字目前仍是估算，不应被当作完成后的 benchmark：

- Qwen Caption 4B 的实际每片段耗时。
- Whisper 在真实中文、英文和混合语言上的吞吐。
- OCR 对字幕密集视频的实际去重比例。
- 四路融合后的热搜索 P95。
- 多模型 Worker 长时间运行的内存斜率。

实施阶段 A 应先用同一批真实媒体逐项运行 10–20 分钟，得到各分析器的单位成本。只有这些数据得到后，才能把本报告中的范围替换为最终实测值。
